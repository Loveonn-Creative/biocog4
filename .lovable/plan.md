# Authenticated invoice journey reliability

## Goal
Make existing uploaded invoices usable from History through Verify, and make each verified record read consistently in Dashboard, MRV, Reports, MONETIZE, and Profile. Preserve guest behavior, existing methods and factors, stored lineage, and the current page structure.

## Release gates
1. **Reconnect saved invoices to verification.** Add a per-invoice action in History that opens Verify with that invoice's actual stored emissions. Show the real stored state: a cached extraction or high confidence is not proof of verification. For invoices without calculable emission rows, show the evidence gap and require a new supported extraction or manual review rather than creating values.
2. **Make Verify the safe synchronization point.** Remove the fabricated “rejected” result for network and permission errors; show an explicit retryable failure instead. Refresh must only reread authorized documents, emissions, verification results and audit records; it must never create rows or recalculate values. Guard repeated verification requests on the server and keep one auditable outcome per emission set, including concurrent requests. Preserve existing historical attempts instead of deleting or rewriting them. Ensure the verified flag and audit evidence agree before reporting success.
3. **Align downstream reads.** Base verified totals and exports on actual verified emission rows and their matching evidence, not unverified records or duplicated verification/ledger attempts. Keep Reports and MONETIZE fresh after successful verification and on manual refresh. Fix the current application insert to carry authenticated ownership, and remove unsupported credit, loan, subsidy, partner and approval claims until real supporting records exist. Do not silently turn an internal application record into a claim that an external partner received it.
4. **Finish account and language reliability.** Change password inside Profile and keep the user on Profile with navigation intact. Use only reviewed static translations for sensitive content; fall back visibly and safely to English when a requested language lacks approved copy, rather than displaying generated text as verified.
5. **Validate each gate.** Run existing MRV regressions before and after changes; add focused tests for idempotent re-verification, duplicate-history reads, missing evidence, and password/locale behavior. Test signed in with existing account data: History → Verify → Refresh → each connected page and a repeated Refresh; confirm the same saved emission IDs and totals, no new rows on Refresh, correct ownership, and no unintended guest change. Deploy only the functions that pass these checks, then verify the live responses and report any limitation that cannot be proven safely.

## Technical boundaries
Existing data already contains repeated verification memberships and duplicate ledger rows; do not bulk-delete, overwrite, or infer which historical attempt is authoritative without a defensible rule. Validate the actual access policies and affected rows before any targeted correction. Changes should stay within the current React pages/hooks and existing verification function unless a database-level concurrency safeguard is required; any necessary schema change needs a separate migration with explicit grants and private RLS. No new climate factors, calculation methods, fabricated records, or guest access changes.
